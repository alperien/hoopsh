## MEDIUM args.ts:51 - Empty-string flag values pass the "loud on malformed input" parser silently
`flagValue` rejects a missing value and a value that starts with `--` (lines 51-57), but accepts the empty string: `--seed ""` returns `''` and runs a batch seeded on base `''` with no warning — exactly the incident class the file header says it exists to close ("a seed that isn't what the caller thinks it is must fail loudly", lines 5-10). `flagNumber` (lines 62-69) compounds it: `Number('')` and `Number(' ')` are `0`, which is finite, so an empty value coerces to zero silently (verified by execution: `flagNumber(['--min-bands',''], ...)` → `0`). The realistic trigger is a quoted-but-unset shell variable (`--min-bands "$FLOOR"` in a CI yaml or wrapper script): the token survives as `''`, becomes `0`, and `0` is cli.ts's documented "disable the gate" value (cli.ts:117-127) — and because the run is calibrated-league/default-endgame/n≥24, none of the three report-only notices at cli.ts:173-179 fires. The acceptance gate is disarmed with zero output saying so, and the run exits 0 regardless of band failures. `--games ""` is caught downstream by cli.ts's own integer≥1 guard, and `--workers ""` dies in resolveWorkerCount — only callers without a second guard (seeds everywhere, `--min-bands`) are exposed. Fix is one line: reject `v.length === 0` (or non-`\S`) in flagValue.
Breaks: the module's documented loud-input guarantee; in the `--min-bands` case, the batch acceptance gate (a gate that cannot fail, silently).

## MEDIUM bench.ts:36 - The ≥1 game/sec budget is printed but never enforced; the perf rung of the verification ladder cannot go red
bench.ts prints `games/sec: X (budget: ≥ 1.0)` and always exits 0 — there is no comparison against the budget anywhere in the file. AGENTS.md:146 lists `npm run bench  # perf budget ≥1 game/sec — hot-path changes` as a rung of the verification ladder, and docs/INTERNALS.md:181 / docs/PLAYBOOK.md:55 repeat it as part of the safety net; CI (.github/workflows/ci.yml) never runs bench at all. So the one perf check in the repo relies entirely on a human reading a number a script printed — an engine regression to 0.1 games/sec passes every documented verification step with exit code 0. This is the exact defect shape cli.ts:160-162 records as "review finding #1" ("the exit code IS the acceptance gate. This used to always exit 0 … which made the calibration rung of the verification ladder decorative") — the perf rung is still decorative. Methodology is otherwise defensible but thin: a single untimed 3-game warmup (adequate — each game is ~10^5 ticks), one wall-clock draw of N=25 with no variance reported, single-threaded so games/sec genuinely equals games/sec/core, and the threshold itself is honest on this hardware class (~3.7 games/sec measured on the 2-core box, docs/history/swarm-plan.md:18, i.e. ~3.7× headroom). A wall-clock draw on a loaded box misreads silently, which is another reason the check should compare-and-exit rather than trust the reader. Cheap fix: `if (N / secs < 1) process.exit(1)` plus a median-of-3 loop.
Breaks: gate honesty of the AGENTS §4.2 perf rung (a documented budget with no failing mode).

## MEDIUM simone.ts:75 - The manual fingerprint the AGENTS workflow prescribes (event count + final score) cannot prove what §4.3 claims it proves
simone.ts:75-76 prints `(N events)` and the FINAL score, and simone.ts:13-14 correctly states this "is the exact fingerprint AGENTS.md's docs-only verification checks". AGENTS.md:137-138 (§4.1) tells every agent to capture exactly that pair, and §4.3 (AGENTS.md:150-155) rests the docs-only and pure-refactor tiers on it — including the claim that a refactor with "fingerprint identical, tests identical … is provable … verified bit-for-bit this way". Count+score is not bit-for-bit: two different event streams can share both (reordered events, changed field values, offsetting scoring changes), so the manual tier can pass a behavior change. The strong instrument exists in this very domain — fingerprint.ts hashes the full events and frames JSON over 28 seeds — but `npm run fingerprint` appears nowhere in AGENTS §4.1-4.3 or the §4.2 ladder; only CONTRIBUTING.md:41 (the human on-ramp) lists it for "refactors claiming no behavior change". The exposure is bounded (CI runs the corpus on every PR; the in-suite flag-off twin in harness/test/fingerprint.test.ts byte-pins one game under `npm test`), but an agent following AGENTS to the letter verifies a "pure refactor" locally with an instrument that cannot detect a count-and-score-preserving change, and the tier's "provable" wording overstates it. Cheap strengthening: have simone print a short sha256 of `JSON.stringify(result.events)` on the same summary line (harness may use node:crypto), and add `npm run fingerprint` to the §4.2 ladder for refactor-tier changes.
Breaks: the documented refactor-verification guarantee's local tier (a marginal "was this behavior-preserving?" decision can flip on a collision the check can't see).

## LOW fingerprint.ts:152 - Verify mode never checks the golden file for entries the corpus no longer generates; buildCorpus silently collapses duplicate seeds

## What is done well

- **The determinism contract in parallel.ts is stated as a contract and then actually enforced.** Seed and mirror derive from the global game index only (parallel.ts:120-129, 184), workers own contiguous slices, results reassemble in slice order, and the floating-point reduction stays in the parent in global order — and test/parallel.test.ts pins worker-count invariance with deep-strict equality through real subprocesses, covering the JSON round trip. The header even corrects its own past overclaim (the L-40 note that only batch/flow are directly exercised).
- **The failure policy has no soft edges.** Any worker failure aborts siblings, rejects the whole run with stderr attached, and keeps the job file with the exact hand-rerun command documented (parallel.ts:39-43, 242-251); envelope echo validation makes truncated or mixed-up worker output unpassable; there is no partial-result path anywhere.
- **The finiteness sweep (parallel.ts:270-304) is a genuinely sharp catch**: JSON.stringify maps NaN/Infinity to null, which would have made workers-N silently diverge from workers-1 by coercing to 0 in the reduction — the guard turns a would-be silent divergence into a loud error, and the comment explains precisely why null is treated as guilty.
- **args.ts encodes incidents, not preferences.** Each rejection rule (missing value, `=` spelling, repeated flag, unknown flag with edit-distance hint) cites the silent failure it closes, and the parser owns the policy even when a caller skips checkFlags.
- **cli.ts's gate is honest about when it is armed.** `--games 0` refused, uncalibrated leagues and the legacy `--no-endgame` path default to report-only and say so, `--endgame` deliberately does NOT disarm (closing a real prior hole), the ratchet floor documents its own history including a reverted temptation to lower it, and sub-threshold runs print why the gate is off.
- **fingerprint.ts is far stronger than a count+score fingerprint**: sha256 over the full event stream AND frames per seed, non-default-config entries (flag-off in both orientations, NCAA, EuroLeague) closing the H-04 hole, and an in-suite twin so plain `npm test` catches flag-off leaks between CI corpus runs.
- **Honesty labeling is mostly exemplary in this domain**: mergeAcc is labeled UNWIRED with a wiring condition and a corrected float-exactness claim; index.ts states outright that the barrel has zero importers and names what is deliberately not exported and why.

## Verified sound

- **Slice tiling**: `per = floor(games/workers)`, first `games % workers` slices carry one extra — sums to `games`, tiles 0..games-1 with no gaps or overlaps (checked algebraically; 8 games / 3 workers → 3/3/2, matching the test's comment).
- **Seed/flip assignment is scheduling-independent**: `${seedBase}-${i}` and `i % 2 === 1` depend only on the global index; no seed-string collisions are possible across indices of one base (integer suffix). Rosters constructed fresh per game inside the worker, so slice start position cannot leak state.
- **FP accumulation order is worker-count invariant**: reduction (accumulate/finalize, reduceFlows) runs in the parent over the globally ordered array; JSON number round-trips are exact for finite doubles (the one lossy case, non-finite→null, is loudly rejected); flow-metrics.ts's reduceFlows documents and preserves array-order folding.
- **Worker lifecycle**: `workers = min(requested, max(1, games))` never spawns more workers than games; workers=1 bypasses subprocesses entirely; AbortSignal on execFile kills children on first failure (no zombies); abort-collateral rejections are reported only when no real failure exists; job temp paths are pid+counter unique. All W subprocesses launch at once but W defaults to cores-1 ('auto' → `max(1, availableParallelism()-1)`), so no oversubscription at defaults.
- **resolveWorkerCount** rejects 0, fractional, and non-numeric loudly (test-pinned) and matches the cli.ts doc claim of a cores-1 default.
- **run-worker.ts** validates task (against GAME_TASK_NAMES, closing the prototype-key hole the same way runGamesInProcess's Object.hasOwn guard does — audit L-39), seedBase, start/count, and league before simulating; stdout carries only the result blob; malformed job JSON exits nonzero and is surfaced by the parent.
- **checkFlags/flagValue**: `=` spellings, repeats, unknown flags (edit-distance ≤2 did-you-mean), and value-is-next-flag all rejected loudly; negative-number values pass through as designed; the Levenshtein implementation is correct (checked the DP recurrence and indexing). cli.ts and flow.ts declare complete vocabularies covering every flag they read, and read order (checkFlags first) is right.
- **cli.ts/CI defaults line up**: CI's `--games 48` ≥ GATE_MIN_GAMES 24 arms the gate; RATCHET_FLOOR 16 is consistent with the measured n=48 fgPct draw-flicker recorded in docs/CALIBRATION.md (16/17 worst case at n=48, 17/17 at n=96); `--endgame`+`--no-endgame` contradiction is refused in both cli.ts and flow.ts.
- **bench.ts games/sec/core definition holds** (single-threaded measurement, so per-core equals total) and the ≥1 threshold is honest on this hardware class (~3.7 games/sec measured, swarm-plan record) — the finding above is about enforcement, not the number.
- **fingerprint.ts `ci-fp` entry matches the CI determinism step's actual game** (flip=false, default rules, frames on — simone runs the same orientation); corpus order/keys are 1:1 with seeds today; verify distinguishes events-hash, frames-hash, and finalScore drift with distinct messages and distinct exit codes (2 missing-golden / 1 mismatch / 0 ok).
- **index.ts exports all exist** (spot-checked every named export against its defining module: run, parallel, aggregate, bands, leagues, season, matchup, league) and the barrel is typechecked by the CI types job; run-worker.ts/sweep-worker.ts/knobs.ts are deliberately unexported as documented; the "zero importers" claim is accurate (examples import by relative path, tests import ../src directly).
- **run.ts↔parallel.ts equivalence today**: runBatch's `boxScore` without paceMinutes equals the parallel NBA path (stats default 48 = NBA.periods × NBA.periodMinutes), and the engine does not mutate Team inputs (agent state is wrapped, teams re-read only), so run.ts's cross-game team-object reuse is currently behavior-identical to parallel's fresh-per-game construction — the MEDIUM above is about the unguarded duplication, not a live divergence.
